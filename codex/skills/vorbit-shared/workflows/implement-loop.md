# Vorbit Implement Loop Workflow

Use for autonomous iteration through a task queue — the branch spec plan's story tasks (spec mode), or Linear sub-issues (Linear mode) — until completion.

1. Load the Vorbit runtime contract and durable rules. Require loop/auto-continue intent plus a queue source: a story (`US-###`) from the branch spec plan at `.vorbit/specs/<branch-slug>/epic.md` (see `../references/spec-files.md` for resolution, status fields, and the worktree-only trade-off), or an explicit Linear issue. Spec mode needs no Linear connection.
2. Resolve runtime storage from `vorbit-resolve-rules` and use `<storage-root>/state/<project-slug>/codex-implement-loop.json`; do not write Claude-specific state into the repository.
3. For cancel: read state, report cancellation in the current session, delete runtime state, and leave code untouched.
4. For resume: never overwrite an existing state. Re-read the source (the story section in `epic.md`, or the Linear parent). If its baseline changed (file modification time, or issue update timestamp), persist `active: false`, `status: needs_input`, and the reason. An inactive `needs_input`, `blocked`, or `failed` state resumes only after the user supplies or confirms the missing resolution; then reconcile, update the baseline, clear failure tracking, reset `iteration` to 1, and set it back to `active: true`, `status: running`.
5. For a new queue, parse the source's `Implementation Order` by phase. Within a phase sort by priority (`P1`/`Urgent`, `P2`/`High`, `P3`/`Normal`, `Low`) then listed or creation order; skip tasks whose `Status` is `done` and terminal issues; accept a flat list as sequential. Append tasks or sub-issues missing from the section as an `unplanned` final phase. If no order exists, build a labeled fallback guess. If a Linear parent has no sub-issues at all, the parent itself is the queue's single executable item.
6. A Parallel marker expresses dependency independence, not permission for concurrent writers. Use isolated worktrees only with explicit approval; otherwise process deterministically. Note: spec files are worktree-local — the whole loop must run in the worktree that holds them.
7. Show the multi-item queue once and confirm Start/Reorder/Cancel before persisting. A single item explicitly started in loop mode begins directly.
8. Persist version, active/status, source baseline, queue entries with phase, current index, completed IDs, iteration/max (50), and repeated-failure fingerprint/count. Write state atomically. In spec mode store the story ID as the parent reference and task IDs (`T#`) as queue entries.
9. For each item, apply the normal implement workflow to that item only: search/reuse, mapped ACs/flows, honest focused test, implementation, regression checks. Mark it started (spec task: set its `**Status:**` line to `in-progress`; Linear: move to In Progress) and report the start in the current session.
10. Mark an item complete (spec task: set `**Status:**` to `done`; Linear sub-issue: Done) only after its ACs and tests pass; record evidence, advance state, and continue. Linear mode: keep the implementation parent In Progress until a PR exists.
11. If the same failure fingerprint repeats three cycles, or 50 iterations are reached, persist `active: false`, `status: blocked`, and the reason, then stop for input. Do not retry blindly. On a blocked spec task, also set its `**Status:**` line to `blocked`.
12. After the queue, verify the story/parent ACs. If covered, report "ready for verification/PR" in the current session, mark runtime state completed, and delete it; in spec mode suggest running `$vorbit-linear-sync` to refresh the Linear summaries. Otherwise persist `active: false`, `status: needs_input`, and the missing ACs rather than inventing work.
13. Report `completed`, `needs_input`, `blocked`, `failed`, or `canceled`, with current item, AC evidence, tests, queue progress, and next action.
